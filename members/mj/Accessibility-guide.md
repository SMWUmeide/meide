개선안은 같은 페이지의 원본 세 화면 오른쪽에 배치했다. 이미지, 주요 색상, 카드 구성과 내비게이션을 재사용했으며 텍스트와 레이어를 편집할 수 있다. 원본 화면은 수정하지 않았다.

**핵심 결과:** 원본 메뉴 상세·영수증의 `#91949E` 텍스트는 흰 배경에서 **3.03:1**, 화면 배경에서 **2.75:1**로 일반 텍스트 기준에 미달한다. 메뉴 상세의 `#74777F` 라벨도 흰 배경에서 **4.48:1**로 미달한다. 해당 텍스트를 기존 `text/secondary` 토큰인 `#626773`로 교체했다.

### 분석 방법과 범위

- Figma 세 화면을 렌더링하여 육안으로 검토하고, 레이어의 색상·투명도·글자 크기·배경·프레임 크기를 읽었다.
- 색 대비는 W3C 상대 휘도 공식으로 직접 계산했다. 스크린샷의 안티앨리어싱 픽셀을 색상값으로 사용하지 않았다.
- 첨부 과제 이미지의 색 대비·폰트·버튼 크기·텍스트·레이블·흐름 점검 항목을 적용했다.
- **Stark, Contrast Checker 플러그인이나 WAVE를 실행한 결과는 아니다.** 이번에 실행한 검사는 Figma 속성 분석·대비 계산·시안 렌더링 검토다. 플러그인과 구현 단계 도구의 재검증 절차는 7절에 제시한다.
- Figma 단위는 시안의 논리 단위다. CSS px, iOS pt, Android dp와 자동으로 동일하다고 가정하지 않는다.
- 이 문서는 세 화면의 설계 검토다. 실제 앱의 접근성 트리, 포커스, 스크롤, 동적 상태는 검증하지 않았으며 전체 앱의 WCAG 적합성을 인증하지 않는다.
- WCAG는 웹 기준이다. 네이티브 앱에서는 대응하는 설계 원칙을 적용하고 플랫폼 접근성 API와 실제 기기로 별도 검증한다.

| 판정 | 의미 |

| 사용성 개선 | WCAG 직접 위반으로 단정할 수 없으나 이해·읽기·조작을 개선할 항목 |

## 3. 색 대비 측정 기록

| 용도 | 전경 / 배경 | 대비 | 일반 텍스트 판정 |
| --- | --- | --- | --- |
| 원본 연한 보조 텍스트 | `#91949E / #FFFFFF` | 3.03:1 | 미달 |
| 원본 영수증 안내 | `#91949E / #F2F4F6` | 2.75:1 | 미달 |
| 원본 메뉴판 라벨 | `#74777F / #FFFFFF` | 4.48:1 | 미달 |
| 원본 홈 전체 보기 | `#646873 / #FFFFFF` | 5.57:1 | 충족 |
| 원본 홈 추천 이유 | `#4C5059 / #ECEEF1` | 6.95:1 | 충족 |

| 개선 사진 안내 글자 | `#FFFFFF / #212121` | 16.10:1 | 충족 |

숫자는 소수 둘째 자리까지 표시하되 판정은 반올림 이전 값으로 한다. 대비 공식은 `(밝은 상대 휘도 + 0.05) / (어두운 상대 휘도 + 0.05)`이다. sRGB 채널을 선형화한 뒤 `L = 0.2126R + 0.7152G + 0.0722B`로 계산했다.

투명도·그라데이션·사진이 있는 경우 실제 합성 배경을 기준으로 검사한다. 메뉴 제목 배경은 `#FFFFFF`에서 `#F2F4F6`까지 변하므로 하나의 정확한 국소 대비값 대신 범위를 표시했다. 사진 위 검정 50% 배경은 흰 사진 부분에서 약 3.98:1까지 떨어질 수 있으므로 불투명 배경으로 개선했다. 이 수치는 현재 사진에서 측정한 최저값이 아니라 밝은 이미지로 교체될 때의 예시다.

일반 텍스트는 **4.5:1**, 큰 텍스트는 **3:1**이 기준이다. 큰 텍스트 기준은 18pt 일반 또는 14pt 굵게(웹에서 대략 24 CSS px 또는 18.67 CSS px 굵게)에 해당하며, 한글 서체의 동등한 크기도 고려한다. 이 앱의 11~17 크기 텍스트에 큰 글자 예외를 일괄 적용하지 않는다. [W3C 대비 기준 해설](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

## 4. 우리 앱 공통 설계 규칙

### 색상과 글자

- 기본 텍스트는 기존 진한 색을 유지한다. 보조 정보에도 `text/secondary = #626773`를 사용하고, `#91949E`를 가격·조건·안내 등 읽어야 할 내용에 사용하지 않는다.
- 사진 위 문구는 안정적인 불투명 배경을 제공한다. 장식용 구분선과 필수 상태 표시는 구별하여 검사한다. 필수 아이콘·상태 식별 정보에는 인접 색 대비 3:1을 적용한다. [W3C 비텍스트 대비 해설](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
- 프로젝트 권장값은 음식명·본문 16 이상, 보조 정보 14 이상, 탭 12 이상이다. 이는 WCAG의 고정 최소 글자 크기 규정이 아니라 이번 앱의 가독성 기준이다.
- 이번 개선 시안은 본문·라벨에 약 1.5배 행간을 사용했다. 고정 높이 때문에 글자가 잘리지 않도록 내용에 따라 카드 높이를 늘린다.
- 원본은 Pretendard다. 편집 도구에서 해당 폰트를 불러올 수 없어 **개선안에만 Noto Sans KR**을 적용했다. 원본 서체로 다시 바꾸면 폭·줄바꿈·높이를 재검증해야 한다.

### 버튼과 조작 영역

- 공통 모바일 목표를 **48×48 논리 단위 이상**으로 잡는다. 실제 구현에서는 iOS pt, Android dp에 맞춘다.
- 아이콘 그림 크기와 클릭 영역을 구별한다. 뒤로 가기 그림은 작아도 바깥 조작 영역을 충분히 확보한다.
- WCAG 2.5.8 AA는 웹에서 **24×24 CSS px** 또는 간격 등 예외를 허용한다. 따라서 44 미만이라는 이유만으로 AA 위반이라고 단정하지 않는다. [W3C 타깃 크기 해설](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)
- Apple은 44×44pt 이상, Google Android는 48×48dp 이상의 터치 영역을 권장한다. 이 앱의 48 목표는 두 플랫폼에서 쉽게 누를 수 있도록 정한 설계 목표다. [Apple UI Design Dos and Don’ts](https://developer.apple.com/design/tips/), [Google Android 접근성 가이드](https://developer.android.com/guide/topics/ui/accessibility/apps)
- 하나의 행동은 하나의 버튼과 포커스로 제공한다. 정보 칩을 버튼처럼 읽게 하지 않는다.

### 레이블과 읽기 흐름

| 요소 | 구현 시 전달할 이름·상태 예시 |
| --- | --- |
| 여행지 선택 | ‘여행지 변경, 현재 이탈리아 키우시’ |
| 추천 음식 카드 | ‘호박·밀알 수프, 상세 보기’ |
| 뒤로 가기 | ‘뒤로 가기’, 버튼 역할 |
| 현재 홈 탭 | ‘홈’, 탭 역할과 선택 상태 |
| 담기 | 화면에 보이는 ‘장바구니에 담기’를 접근성 이름에 포함 |
| 영수증 합계 | ‘예상 합계 46.80유로, 물 제외, 팁 포함’ |

화면 제목 → 주요 내용 → 행동 순으로 탐색되게 하고, 화면 전환 후에는 새 제목을 인지할 수 있게 한다. 메뉴판 정보와 AI 추정의 제목·그룹 구조를 읽기 순서에도 유지한다. 일반 웹 구현에서는 제목·버튼·목록 등 기본 요소를 우선 사용한다. [WCAG 2.2의 구조·순서·이름 및 상태 기준](https://www.w3.org/TR/WCAG22/)

## 5. 개선 시안 반영 범위

| 구분 | 완료한 작업 | 남은 작업 |
| --- | --- | --- |
| 시각 대비 | 확인된 회색 텍스트를 기존 보조 텍스트 토큰으로 교체, 사진 안내 불투명 배경 적용 | 실제 앱의 다크 모드·눌림·비활성·로딩 상태 검사 |
| 글자와 레이아웃 | 작은 라벨 확대, 본문 줄바꿈, 재료 칩 줄바꿈, 안내문 높이 조정 | OS 큰 글자, 200% 확대, 좁은 화면에서 검사 |
| 조작 | 전체 보기 높이 48, 뒤로 가기 48×48, 담기 단일 버튼 | 실제 터치 범위, 키보드·스위치 접근 검증 |
| 내용 | 영수증 팁 기준과 합계 조건 표시, 예상값 안내 강화 | 데이터 변경 시 문구 동기화, 알레르기 요약 추가 검토 |
| 보조기술 | 문서에 이름·역할·상태와 읽기 흐름 명세 | VoiceOver·TalkBack·웹 접근성 트리 구현 및 테스트 |

개선 시안의 긴 프레임은 전체 콘텐츠를 보여 주기 위한 것이다. 실제 기기에서 화면 전체를 축소해 맞추지 말고 세로 스크롤로 제공한다. Figma에서 보이는 단일 해상도 렌더링이 확대·스크롤 테스트를 대신하지 않는다.

## 6. 구현 후 완료 기준

| 검사 | 방법 | 통과 조건 |
| --- | --- | --- |
| 텍스트 대비 | 실제 렌더링의 전경·합성 배경 검사 | 일반 글자 4.5:1 이상. 큰 글자 예외는 크기·굵기 확인 후 적용 |
| 글자 확대 | 웹 200% 텍스트 확대, 네이티브 OS 글자 크기 확대 | 가격·재료·안내·버튼 이름이 잘리지 않고 기능 유지 |
| 리플로 | 웹에서 폭 320 CSS px 또는 1280px 화면의 400% 확대 | 해당 콘텐츠를 가로·세로 두 방향으로 스크롤하지 않고 읽음 |
| 텍스트 간격 | 웹에서 행간 1.5배, 문단 뒤 2배, 자간 0.12em, 단어 간격 0.16em 적용 | 내용·기능 손실 없음. 언어에 적용 가능한 속성 사용 |
| 터치 | 가장자리까지 실제 탭 동작 확인 | 문서의 48 목표를 구현 단위로 충족하고 인접 버튼 오작동 없음 |
| 읽기 순서 | VoiceOver·TalkBack 순차 탐색 | 음식명→설명, 메뉴명→금액, 합계→조건의 관계 유지 |
| 키보드·포커스 | 웹 또는 지원 플랫폼의 키보드로 주요 흐름 수행 | 이동·실행 가능, 포커스 표시 식별 가능, 하단 바가 포커스를 완전히 가리지 않음 |
| 동적 알림 | 메뉴 담기 후 상태 확인 | 중복 추가 없이 성공을 인지하고 탐색 위치를 잃지 않음 |

확대는 [1.4.4 Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html), 좁은 폭은 [1.4.10 Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), 간격 조정은 [1.4.12 Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)을 따른다. 1.4.12의 수치는 기본 디자인에 무조건 적용할 스타일이 아니라 사용자가 덮어써도 내용이 유지되어야 하는 시험 조건이다.

## 7. 과제용 검사 절차와 증거 기록

1. 위 표의 원본·개선안 링크를 열어 같은 요소를 비교한다.
2. Figma에서 Contrast Checker 또는 Stark를 사용할 수 있다면 전경·실제 배경을 지정해 3절 색상 쌍을 재검증한다. 사진·투명도·그라데이션은 자동 판정의 배경 선택이 맞는지 확인한다.
3. 글자 크기, 버튼 외곽 영역, 줄바꿈은 Figma 속성 패널에서 확인한다. 플러그인 검사 결과만으로 실제 클릭 영역을 확정하지 않는다.
4. 구현된 웹 화면이 있으면 WAVE로 레이블·구조·대비를 검사한다. Figma 편집기 URL을 검사해서 우리 앱의 결과라고 제출하지 않는다. WAVE는 웹 콘텐츠 평가 도구다. [WAVE 공식 안내](https://wave.webaim.org/)
5. 네이티브 앱은 VoiceOver·TalkBack과 플랫폼 검사 도구로 수동 검증한다. 자동 검사에서 오류가 없어도 6절의 사용자 흐름을 직접 수행한다.
6. 각 검사에 화면·노드·기기·글자 크기 설정·도구·날짜·수정 전후 결과를 기록한다.

| 이슈 | 이번에 확보한 증거 | 추가로 확보할 증거 |
| --- | --- | --- |
| M01·M02·R01·R02 | 원본 색상·배경·크기와 계산값, 개선안의 토큰 변경 | 실제 앱 대비 결과 |
| H01·M04·M06 | 원본/개선 조작 영역의 레이어 크기, 단일 버튼 구조 | 실제 탭·키보드·보조기술 동작 |
| H02·H03·R04 | 글자 확대 및 줄바꿈 후 시안 렌더링 | OS 확대·웹 200%·좁은 폭 화면 캡처 |
| H04·M05·R05 | 화면 구조와 명세 | 읽기 순서·그룹·선택 상태 테스트 기록 |

우선순위는 **핵심 정보 대비 수정 → 버튼·레이블 정리 → 확대·읽기 순서 검증**이다. 대비를 개선했다는 이유로 미검증 항목을 모두 완료 처리하지 않는다.

## 8. 참고 자료

모두 2026-11-16에 확인한 공식 자료이며, 기업 권장사항과 WCAG 요구사항을 구별해 적용했다.

- [W3C — WCAG 2.2](https://www.w3.org/TR/WCAG22/): 기준 번호·이름·적합 수준의 원문.
- [W3C — Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html): 텍스트 대비·큰 글자·휘도 계산.
- [W3C — Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html): 필수 UI 식별 정보·상태 대비.
- [W3C — Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum): 24 CSS px와 예외.
- [Apple — UI Design Dos and Don’ts](https://developer.apple.com/design/tips/): 터치 영역, 읽기, 간격에 대한 기업 설계 지침.
- [Google — Make apps more accessible](https://developer.android.com/guide/topics/ui/accessibility/apps): Android 터치 영역·레이블·접근성 구현 지침.
- [WAVE — Web Accessibility Evaluation Tools](https://wave.webaim.org/): 구현된 웹 화면의 자동 검사와 사람의 평가를 함께 수행하기 위한 도구.
